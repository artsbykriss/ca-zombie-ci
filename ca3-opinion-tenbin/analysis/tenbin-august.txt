1.1.
Executive Summary
Zellic conducted a security assessment for Tenbin Labs from August 4th to August 11th, 2026.
During this engagement, Zellic reviewed Tenbin's code for security vulnerabilities, design issues,
and general weaknesses in security posture.
1.2.
Goals of the Assessment
In a security assessment, goals are framed in terms of questions that we wish to answer. These
questions are agreed upon through close communication between Zellic and the client. In this
assessment, we sought to answer the following questions:
• Does GenericMorphoAdapter accurately report the realizable value of its ERC-4626
position and enforce appropriate slippage bounds during allocation and deallocation?
• Can an unauthorized party move, rescue, strand, or redirect the underlying assets or
vault shares managed by GenericMorphoAdapter or cause a parent vault to use an
unintended adapter?
• Does BebopHook ensure that each Bebop RFQ fill and Tenbin Controller order agree on
the action, token pair, amounts, payer, recipient, authorized market maker, and signed
exchange rate?
• Do Bebop-backed mint and redemption transactions settle atomically without leaving
reusable approvals, residual balances, or user funds stuck in the hook or router?
• Does CrossChainERC4626Adapter correctly decode and validate the source chain,
sender, action, tokens, beneficiary, and cooldown identifier for every cross-chain
message?
• Do authorization changes, including account restrictions, remain effective throughout
the cooldown life cycle?
• Can deposit, cooldown, unstake, cancellation, delivery, or failed-message recovery
paths reach an unrecoverable state, strand assets, or process the same position more
than once?
1.3.
Non-goals and Limitations
We did not assess the following areas that were outside the scope of this engagement:
• Front-end components
• Infrastructure relating to the project
• Key custody
Due to the time-boxed nature of security assessments in general, there are limitations in the
coverage an assessment can provide.

2.2.
Methodology
During a security assessment, Zellic works through standard phases of security auditing,
including both automated testing and manual review. These processes can vary significantly per
engagement, but the majority of the time is spent on a thorough manual review of the entire scope.
Alongside a variety of tools and analyzers used on an as-needed basis, Zellic focuses primarily on
the following classes of security and reliability issues:
Basic coding mistakes. Many critical vulnerabilities in the past have been caused by simple,
surface-level mistakes that could have easily been caught ahead of time by code review.
Depending on the engagement, we may also employ sophisticated analyzers such as model
checkers, theorem provers, fuzzers, and so on as necessary. We also perform a cursory
review of the code to familiarize ourselves with the contracts.
Business logic errors.
Business logic is the heart of any smart contract application.
We examine the specifications and designs for inconsistencies, flaws, and weaknesses
that create opportunities for abuse. For example, these include problems like unrealistic
tokenomics or dangerous arbitrage opportunities.
To the best of our abilities, time
permitting, we also review the contract logic to ensure that the code implements the
expected functionality as specified in the platform's design documents.
Integration risks. Several well-known exploits have not been the result of any bug within
the contract itself; rather, they are an unintended consequence of the contract's interaction
with the broader DeFi ecosystem. Time permitting, we review external interactions and
summarize the associated risks: for example, flash loan attacks, oracle price manipulation,
MEV/sandwich attacks, and so on.
Code maturity. We look for potential improvements in the codebase in general. We look
for violations of industry best practices and guidelines and code quality standards. We
also provide suggestions for possible optimizations, such as gas optimization, upgradability
weaknesses, centralization risks, and so on.

3.1.
Using convertToAssets will overstate adapter value for fee-charging vaults
Target
GenericMorphoAdapter
Category
Integration Risks
Severity
Medium
Likelihood
Low
Impact
Medium
Description
The realAssets() function values the adapter's ERC-4626 share balance by calling
vault.convertToAssets(balance). ERC-4626 requires convertToAssets() to exclude fees,
while previewRedeem() must include withdrawal fees. Consequently, when the configured
ERC-4626 vault charges a withdrawal fee, realAssets() reports more assets than the adapter
could obtain by redeeming its shares.
function realAssets() public view returns (uint256) {
uint256 balance = vault.balanceOf(address(this));
return vault.convertToAssets(balance);
}
Impact
The parent Vault V2 includes each adapter's realAssets() value when calculating its total assets
and share price. The overstated value can therefore be reflected in the parent vault's accounting
before the withdrawal fee is realized. A user redeeming against available liquidity may receive
assets based on this gross value, while a later deallocation realizes the fee and leaves the shortfall
to the remaining vault share holders. The discrepancy is proportional to the underlying vault's
withdrawal fee and occurs only when GenericMorphoAdapter is configured with a fee-charging
ERC-4626 vault.
Recommendations
Replace vault.convertToAssets(balance) with vault.previewRedeem(balance) so that the
reported value includes withdrawal fees and reflects the assets obtainable by redeeming the
adapter's current share balance.

3.3.
Floor rounding in the rate-bound check breaks the signed-quote invariant
Target
BebopHook
Category
Coding Mistakes
Severity
Low
Likelihood
Low
Impact
Low
Description
The verifyHookData() function enforces that the fill rate does not exceed the market maker's
signed quote by computing Math.mulDiv(outputAmount, data.quoteInputAmount,
inputAmount) and comparing the result with data.quoteOutputAmount. The three-argument
Math.mulDiv() rounds down. When outputAmount * quoteInputAmount is not evenly divisible
by inputAmount, the computed quotient can equal quoteOutputAmount even though the exact rate
is greater than the signed bound.
if (Math.mulDiv(outputAmount, data.quoteInputAmount, inputAmount) >
data.quoteOutputAmount) {
revert InvalidAmount();
}
Specifically, when
outputAmount * quoteInputAmount = quoteOutputAmount * inputAmount + r
for some 0 < r < inputAmount, floor division returns exactly quoteOutputAmount. The
comparison is therefore false, and the fill is accepted despite violating the exact inequality.
Impact
A fill can settle at a rate that is strictly above the market maker's signed limit. The normalized value
discarded by floor division is less than one smallest unit of quoteOutputAmount; the
corresponding excess in outputAmount is less than inputAmount / quoteInputAmount units.
Although this is a bounded rounding discrepancy rather than an unbounded loss path, it breaks
the signed-rate invariant enforced by the hook.
Recommendations
Round the quotient up before comparing it with the signed limit. For positive amounts, the
rounded-up result exceeds quoteOutputAmount whenever the exact rational value exceeds it,

3.5.
Missing identity validation allows self-referential adapter deployment
Target
GenericMorphoAdapter
Category
Coding Mistakes
Severity
Informational
Likelihood
N/A
Impact
Informational
Description
The GenericMorphoAdapter constructor verifies that vault_ and parentVault_ use the same
underlying asset but does not require them to be distinct addresses. If both parameters contain
the parent Vault V2 address, the AssetMismatch check passes and the adapter deploys
successfully.
constructor(address parentVault_, address vault_, address owner_)
Ownable(owner_) {
parentVault = IVaultV2(parentVault_);
vault = IERC4626(vault_);
asset = parentVault.asset();
// Passes trivially if vault_ == parentVault_: same address, same asset()
if (vault.asset() != parentVault.asset()) revert AssetMismatch();
[...]
}
The adapter must then be registered through the timelocked addAdapter() path before any
impact occurs. Once registered, the following call sequence recurses until the transaction runs
out of gas:
VaultV2.accrueInterestView()
−> GenericMorphoAdapter.realAssets()
−> parentVault.convertToAssets()
−> VaultV2.previewRedeem()
−> VaultV2.accrueInterestView()
Vault V2 uses the transient storage variable firstTotalAssets as an intratransaction short circuit.
However, accrueInterest() sets it only after accrueInterestView() returns. The recursive call
therefore occurs before the short circuit is initialized.
The deposit(), mint(), withdraw(), redeem(), and allocate() paths call accrueInterest()
directly and consequently revert. Deallocation also fails because
GenericMorphoAdapter.deallocate() calls withdraw() on the same parent vault, which enters
the recursive accounting path.

3.6.
Stale cooldown ownership entries are not cleared after terminal actions
Target
CrossChainERC4626Adapter
Category
Coding Mistakes
Severity
Informational
Likelihood
N/A
Impact
Informational
Description
The cooldownAccounts mapping records the originating sender of a cross-chain COOLDOWN action
so that only that sender can later submit UNSTAKE or CANCEL_COOLDOWN for the same
(sourceChainSelector, cooldownId) pair. Neither terminal action removes the entry after
successful execution, so the ownership record persists indefinitely.
When a COOLDOWN is initiated, ownership is recorded:
[...]
if (action == Action.COOLDOWN) {
cooldownAccounts[message.sourceChainSelector][id]
= bytes32(message.sender);
emit CrossChainCooldownCreated(...);
}
[...]
After UNSTAKE or CANCEL_COOLDOWN completes successfully,
cooldownAccounts[sourceChainSelector][cooldownId] is never deleted. The authorization
entry remains set to the original sender even though the underlying cooldown has been
consumed.
Impact
There is no direct asset impact because StakedAsset deletes the underlying cooldown during
either terminal action. A replay reaches StakedAsset.unstake() or
StakedAsset.cancelCooldown() and reverts with ZeroCooldownAssets() before any additional
assets can be released. The remaining entry is stale authorization state with no operational use
and can make the public ownership mapping appear to describe an active cooldown after that
cooldown has ended.

Obsolete fee role constants remain after fee functionality was removed
Target
CrossChainERC4626Adapter
Category
Coding Mistakes
Severity
Informational
Likelihood
N/A
Impact
Informational
Description
The scoped changes remove the adapter's fee-configuration functions, fee-collection logic,
fee-withdrawal function, and constructor role grants. However, CrossChainERC4626Adapter still
declares the corresponding FEE_SETTER_ROLE and FEE_COLLECTOR_ROLE constants:
bytes32 public constant FEE_SETTER_ROLE = keccak256("FEE_SETTER_ROLE");
bytes32 public constant FEE_COLLECTOR_ROLE = keccak256("FEE_COLLECTOR_ROLE");

bytecode and may lead operators or integrators to believe that the adapter still supports fee
configuration and collection.
Recommendations
Remove FEE_SETTER_ROLE, FEE_COLLECTOR_ROLE, and the remaining assetFees documentation
references if fee management is no longer supported. If fee management is intended to remain,
restore the complete fee configuration, collection, withdrawal, and role-assignment paths rather
than retaining role identifiers alone.

payload-processing changes, and related event updates.
Cross-chain cooldown support
The adapter was extended to support staked-asset cooldown life-cycle operations via Chainlink
CCIP, replacing the previous deposit/redeem binary with a four-action dispatch model.
• A new Action enum with variants DEPOSIT, COOLDOWN, UNSTAKE, and CANCEL_COOLDOWN
was added.
• The Payload struct's target field was replaced with actionAndId.
• A new cooldownAccounts mapping (uint64 chain => uint256 id => bytes32
account) binds each cooldown ID to the originating chain and sender, enforcing that
only that account can later UNSTAKE or CANCEL_COOLDOWN.
• The processMessage function now validates token counts by Action; CANCEL_COOLDOWN
and UNSTAKE require zero inbound tokens, while DEPOSIT and COOLDOWN require exactly
one.
• After _processPayload returns, COOLDOWN stores the initiator in cooldownAccounts and
emits CrossChainCooldownCreated. All other actions follow the existing
return-to-source or local-delivery path.
Vault model refactoring (single-vault, immutable)
The dynamic target allowlist was replaced with a single immutable vault configured at deployment.
• Two new immutable variables, VAULT and ASSET, are set in the constructor.
• The enabledTargets allowlist mapping was removed along with setTargetEnabled
and the TargetEnabled event.
• The constructor's feeSetter and feeCollector parameters were replaced with a
single vault parameter. Role grants for FEE_SETTER_ROLE and FEE_COLLECTOR_ROLE
were also removed.
• A new InvalidVault error guards against a zero-address vault at construction.
