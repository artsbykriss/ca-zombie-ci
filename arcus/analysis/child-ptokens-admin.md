## 2. Empty token pTEST3 (`0x122408C1399E51C41B096402fea46e20E762A950`) — first-deposit analysis

Observed (live `eth_call`, and trace-verified):

* `convertToShares(1e6)` = **1e16**; `convertToShares(1)` = **1e10**; `convertToAssets(1e18)` = **1e8** (=100 USDG).
* `maxDeposit(account)` = `maxMint(account)` = `maxRedeem(account)` = **0** for every tested account
  (dead, deployer, manager, Safe, NAV signer, team EOA, both allowlisted traders).
* `deposit(1e6, *)` from any tested sender reverts with **custom error `0x6565c4ec(1_000_000, 0)`**
  (amount, quota) — i.e. "deposit exceeds remaining quota".
* Formula verified **exactly** on three tokens:
  `shares = assets * (TS + vs) * 1000 / (TA_stored + 1)`, `TA_stored = totalAssets*1000` (pToken ns+0x0a),
  `vs` = pToken ns+0x07 (**1e7**; pTEST = 1e9). `convertToAssets` is the algebraic inverse.
  So the virtual offsets are 1e7 shares (10^-11 share) and `+1` stored-asset unit (= 0.001 raw USDG = 1e-9 USDG).

**First-depositor inflation potential: none exploitable by outsiders.**
1. Deposits are **per-(token, account) quota-gated** inside the pToken: the quota struct at pToken namespace
   `0xd9fd…2a00 + 0x12` = `{uint256 assetQuota; uint256 shareQuota}`. `maxDeposit(account)` returns the remaining
   `assetQuota`; `maxMint(account)` returns the remaining `shareQuota`. Verified end-to-end: `deposit(1e6)` by
   `0x001232c6` on pBTC3x succeeded and consumed both fields 1:1 (assetQuota 1e8→99e6; shareQuota −9.975e15).
   For pTEST3 every account has both fields = 0 → nobody (not even operator EOAs with factory allow flags) can
   execute the first deposit; `deposit()` reverts `0x6565c4ec(amount, quota)`.
2. **The minted share amount is the pre-granted `shareQuota`, not a live `convertToShares` computation.**
   Proven by state-override experiments on the fork: overriding `shareQuota` to 1e10 / 5e15 / 2e16 and depositing
   1e6 assets minted exactly 1e10 / 5e15 / 2e16 shares (and decremented a global share-credit counter at slot
   `0x2d8b0fc4…0017` 1:1). The observed grant for `0x001232c6` on pBTC3x equals `assets·1e10·(1−fee)`
   (the empty-vault virtual-offset rate) — 1.757× the current live `convertToShares` rate, i.e. quota credits are
   fixed-value share amounts set by the privileged grant, decoupled from current NAV. No USDG transfer is executed
   inside `deposit()` in simulation (settlement runs via the separate deposit router; NAV via privileged paths).
3. `totalAssets` is **stored NAV**, not token balance — donating USDG to the token does not move `totalAssets`,
   unlike classic ERC-4626 inflation attacks.
4. The factory additionally gates eligibility: `isAllowed(token,account)` (`0x1c0d9bca`) = per-token map
   `ns+0x05[token][account]` OR global map `ns+0x06[account]`; pTEST3 has zero entries in either for all tested accounts.
5. Residual risk is **privileged-only**: quota grants (asset+share amounts) decide both who may deposit and at what
   share value. With the 1e7-share virtual offset and a 0-state vault the first minter gets ~1e16 shares per USDG.
   Whether a grant is “fair” depends on the grant rate vs live NAV at deposit time — for the single live example
   (pBTC3x/0x001232c6) the depositor receives 1.757× the shares the live conversion would give (small dilution of
   existing holders, bounded by the 100 USDG quota).

## 5. Corrections to the parent's conclusions

1. **"0x4e666f20 … today it reverts from that EOA [deployer]" — wrong.** The deployer still holds roleB
   (`0xfb488cd4…`) and `0x4e666f20` **succeeds** from it today (verified by `eth_call` and a state-diff trace
   that wrote struct+1). What the deployer lost: roleA (block 51,224,866) and DEFAULT_ADMIN (block 51,213,956);
   calls that revert from it are `upgradeToAndCall`, `setBeacon`, `setBridgeVault`, `8da87eb1`, `setManager`.
2. **Signatures:** `0xfe618ab1` is `(address[],bool)` (not `(uint256,uint256)`); `0xd3c5ee0e` is
   `(address,address[],bool)` (not `(address,uint256,address[])`); `0xd85777d0` is `(uint256,address[],uint256[])`.
3. **Two extra factory roles were missed:** roleA `0xb91dda2c…` (setManager, token creation) and
   roleB `0xfb488cd4…` (limit updates, token enable, allowlists — the role most operator calls use).
   roleB members include the (still-active) deployer and two team EOAs — the "single EOA" risk surface is broader
   than just the NAV signer.
4. **"Bridge vault"** `0xD42c46c7…` is labeled **"Deposit router"** by HoodScan; factory field name is `bridgeVault`.
5. **depositsPaused=false ≠ depositable.** All pToken deposits are additionally quota-gated per (token, account)
   (ns+0x12); pTEST3 has zero quotas, and the manager EOA has no factory privileges at all.
6. NAV_SIGNER_ROLE hash confirmed as keccak("NAV_SIGNER_ROLE") = `0x2fc965e6…` (matches parent).
