6. 1.0.0/1.0.1 vs 1.0.2/1.0.3 discrimination — honest limitation
--------------------------------------------------------------------------------
The 1.0.x family markers are present in 1.0.0, 1.0.1, 1.0.2, 1.0.3 alike, so the
deployed ELF cannot be narrowed to the vulnerable 1.0.0/1.0.1 subset from strings.
Candidate patch discriminators were checked against anchor-lang crate sources
(/tmp/opencode/anchor-src/anchor-lang-1.0.0..1.0.3):
  strings only in 1.0.2+ (not 1.0.0/1.0.1):
    "non-system key must be rejected"
    "system program account must be accepted"
    "non-executable account must be rejected"
    "any executable account must be accepted"
    "unexpected error variant: {other:?}"
    "init-if-needed"
  -> ALL of these live inside #[cfg(test)] mod tests (src/accounts/program.rs
     lines 251-326) or tests/seeds_compile.rs, i.e. NOT compiled into a release
     (cargo build-sbf) binary. They are NOT usable as deployed discriminators.
  The 1.0.2 fix itself (removing the `T::id()==Pubkey::default()` special case in
  TryFrom<&AccountInfo> for Program<T>) adds no unique non-test string, so the
  deployed ELF carries no reliable 1.0.1-vs-1.0.2 marker.
Conclusion: report the family ANCHOR_1_0_X. Subset inference only via deploy
timing: all four 1.0.x programs were last deployed AFTER the 2026-05-02 1.0.2
release (2026-09-11 .. 2026-10-22), which is consistent with a rebuild on
>=1.0.2 (fixed), but this is INFERENCE, not proof from the binary.

Marker presence verification (source-level, /tmp/opencode/anchor-src):
  "IDL account must be empty in order to resize, try closing first": 0.29 YES,
     0.30 YES, 1.0.1 NO
  "The program was compiled without idl instructions": 0.29 YES(2), 0.30 YES(2),
     1.0.1 NO
  "interface-instructions": 0.29 NO, 0.30 YES, 1.0.1 NO
  -> "<=0.32" bucket is correct as "not 1.0.x" but includes pre-0.30 versions
     (2022 chainlink deploys are actually ~0.24-0.29).
